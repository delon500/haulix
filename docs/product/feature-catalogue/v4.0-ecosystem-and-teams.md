# Feature Catalogue — v4.0 Ecosystem and Teams

v4.0 turns the app into a platform others build on, and opens it to households, teams and businesses: 18 features (F-106–F-123). It's an ongoing phase rather than a single release. This file introduces a fourth persona, Lerato, an IT manager at a 200-person media company who buys and runs software for her staff.

## Developer platform

These five features let developers and power users script, extend and connect the app to anything.

### F-106 CLI tool

**Integrations and developer · v4.0 · Free**

**What it is:** A command-line tool for controlling the engine from a terminal or script: add downloads, manage queues, check status and change settings. It talks to the same engine as the desktop app, locally or on a server.

**User story:** As Sam, I want to control downloads from my terminal and shell scripts, so that I can automate them alongside my other server tasks.

**Scenario:** Sam writes a nightly script that runs a command to queue his backup archives, waits for them to finish, then checks their status. The same downloads appear in his desktop app and phone.

**Acceptance criteria:**

- Commands for adding links, listing and controlling downloads and queues, viewing status, and changing settings.
- Works with a local or remote engine, using a secure access token for remote ones.
- Output can be plain text for people or JSON for scripts.
- Clear exit codes so scripts can detect success or failure.
- Available for Windows, macOS and Linux, and included in the Docker image.

### F-107 Public REST/WebSocket API

**Integrations and developer · v4.0 · Pro**

**What it is:** A documented programming interface to the engine, so other apps and scripts can add downloads, read status and receive live updates. It's the same interface the app's own desktop, web and mobile clients use.

**User story:** As Sam, I want a documented API for my download engine, so that I can connect it to my home automation and my own tools.

**Scenario:** Sam builds a small dashboard for his home server that shows active downloads next to other system stats, using the API's live updates.

**Acceptance criteria:**

- REST endpoints for downloads, queues, rules, subscriptions, library and settings.
- A WebSocket feed for live progress and events.
- Access controlled by API keys with limited permissions (for example, read-only).
- Full documentation, with an OpenAPI description and examples.
- Versioned, so updates don't break existing integrations without warning.

### F-108 Webhooks and Zapier/n8n integration

**Automation · v4.0 · Pro**

**What it is:** The app can notify other services when something happens (a download finishes or fails, a subscription finds new items), and connects to automation platforms like Zapier and n8n so users can link it to thousands of other apps without coding.

**User story:** As Diego, I want a message posted to my team chat whenever client footage finishes downloading, so that my editor knows it's ready without me telling them.

**Scenario:** Diego builds a Zapier automation: when a download in the "Client" queue finishes, post the filename in the team's channel and add a row to the project spreadsheet.

**Acceptance criteria:**

- Webhooks for events: download finished, failed, started, subscription found new items, budget reached.
- Each webhook can be limited to particular queues or rules.
- Webhook messages are signed so receivers can confirm they're genuine.
- Failed deliveries are retried with increasing delays and logged.
- Official integrations published for Zapier and n8n.

### F-109 Scriptable hooks (JavaScript or Python)

**Automation · v4.0 · Pro**

**What it is:** Small scripts that run inside the app at key moments, such as before a download starts or after it finishes, to make custom decisions: rename files using complex logic, skip certain items, or post-process content.

**User story:** As Sam, I want to run my own logic when downloads finish, so that I can handle unusual cases that rules can't express.

**Scenario:** Sam writes a short script that runs after each podcast download: it reads the episode number from the title, renames the file to his library's format, and moves it into the right season folder.

**Acceptance criteria:**

- Hooks run at defined points: link added, before download, after download, after post-processing.
- Scripts can be written in JavaScript or Python and run in a sandbox with limited permissions.
- Scripts declare what they need (file access, network), and the user approves it when installing them.
- Errors in a script are logged and never crash the app or lose the download.
- Example scripts and documentation are provided.

### F-110 Plugin marketplace (WebAssembly)

**Integrations and developer · v4.0 · Free**

**What it is:** An in-app store where users can browse and install plugins made by the community or companies: new site support, post-processors, integrations, outage schedules and more. Plugins run in a secure sandbox (using WebAssembly), so they can't harm the user's computer.

**User story:** As Sam, I want to install community plugins safely from inside the app, so that I can add capabilities without trusting random code from the internet.

**Scenario:** Sam browses the marketplace and installs a plugin that sends finished movies to his media server. The install screen lists exactly what it can access (one folder and his media server's address), and he approves.

**Acceptance criteria:**

- In-app browsing with search, categories, ratings, reviews and install counts.
- Every plugin is sandboxed and must declare its permissions, shown to the user before install.
- Plugins are reviewed and signed before listing, and can be removed remotely if found harmful.
- Plugins update automatically, with permission changes requiring the user's approval.
- A developer kit with documentation, templates and a testing tool.

## Integrations and migration

These three features connect the app to the tools people already use, and make switching from competitors painless.

### F-111 Integrations with Plex, Jellyfin, Emby, Calibre, Obsidian and Notion

**Integrations and developer · v4.0 · Pro**

**What it is:** Ready-made connections to popular apps: media servers (Plex, Jellyfin, Emby) see new videos straight away, Calibre receives downloaded ebooks, and note apps (Obsidian, Notion) receive transcripts and summaries.

**User story:** As Maya, I want lecture summaries sent to my Obsidian notes automatically, so that my study notes and lectures live in one place.

**Scenario:** Maya connects her Obsidian vault. Each new lecture now creates a note with its title, summary, key points and a link back to the video. Sam, meanwhile, connects Jellyfin, which refreshes its library each time a show finishes downloading.

**Acceptance criteria:**

- Media servers: new files trigger a library refresh in Plex, Jellyfin and Emby.
- Calibre: downloaded ebooks are added to the chosen Calibre library with metadata.
- Obsidian: transcripts and summaries are saved as Markdown notes in a chosen folder, using a template.
- Notion: summaries are added as pages in a chosen database.
- Each integration is set up once in settings and can be limited to certain queues, tags or rules.

### F-112 Import from IDM, JDownloader and FDM

**Integrations and developer · v4.0 · Free**

**What it is:** A one-click importer that brings over a user's queues, unfinished downloads, history and settings from Internet Download Manager, JDownloader or Free Download Manager, so switching costs nothing.

**User story:** As a long-time IDM user, I want to bring my unfinished downloads and settings across, so that switching doesn't mean starting from scratch.

**Scenario:** A new user installs the app. It detects IDM and offers to import. In one click, her 40 queued links, 3 partly finished downloads, speed limits and folder settings appear in the new app.

**Acceptance criteria:**

- Detects installed IDM, JDownloader and FDM and offers to import during setup or from settings.
- Imports queued links, history, folder settings and speed limits where the other app stores them.
- Partly finished downloads resume from where they were if the server supports it.
- Shows a summary of what was imported and anything that couldn't be.
- Never changes or deletes anything in the other app.

### F-113 Telegram, Discord or email notifications

**Notifications · v4.0 · Pro**

**What it is:** Alerts (feature F-096) can also be sent to Telegram, Discord or email, for people who live in those apps or want alerts on a device without the companion app.

**User story:** As Sam, I want server alerts in my Telegram, so that I see them alongside my other home-lab notifications.

**Scenario:** Sam connects his Telegram account. When his NAS engine goes offline or a subscription finds new episodes, a message from the app's Telegram bot appears in his chat.

**Acceptance criteria:**

- Connects to Telegram (via a bot), Discord (via a webhook or bot) and email.
- Each alert type can be routed to any of these channels.
- Messages are short and include a link to open the relevant download in the web dashboard.
- Users can test each channel with a sample message during setup.
- Rate limits prevent floods when many events happen at once.

## Households and teams

These three features let several people share one engine, one queue and one library, each with their own access.

### F-114 Shared queues for households and teams

**Sharing and collaboration · v4.0 · Team**

**What it is:** Several people, each with their own account, can add downloads to the same engine and see shared queues. Each download shows who added it.

**User story:** As Diego, I want my editors to add downloads to our studio's shared engine, so that everyone's files download on the fast studio connection and land on the shared drive.

**Scenario:** Diego's three editors each send links from their own laptops to the studio's engine. The shared "Studio" queue shows every download with the name of the person who added it.

**Acceptance criteria:**

- An engine owner can invite others by email to join as members.
- Members can add to shared queues and see their own downloads; owners and admins see everything.
- Each download shows who added it and when.
- Members can also keep private queues only they can see.
- Removing a member stops their access immediately.

### F-115 Per-user limits and permissions

**Sharing and collaboration · v4.0 · Team**

**What it is:** Owners and admins control what each person can do on a shared engine: which queues they can use, how much data or bandwidth they get, and whether they can change settings or rules.

**User story:** As a parent running the family engine, I want to give my children limited data and no access to settings, so that the household budget isn't used up and nobody changes things by accident.

**Scenario:** Priya sets her teenage son's account to 20 GB a month, normal priority, with no access to settings. When he reaches his limit, his downloads pause and Priya gets an alert.

**Acceptance criteria:**

- Roles: owner, admin, member and viewer, each with clear default permissions.
- Per-user limits on data, speed, number of active downloads and queues they can use.
- Permissions to change settings, rules and subscriptions can be granted or removed per user.
- Users see their own usage against their limits.
- Changes to permissions take effect immediately.

### F-116 Shared libraries and collections

**Sharing and collaboration · v4.0 · Team**

**What it is:** Collections, tags and transcripts can be shared with other members, so a team or family builds one library together, such as a shared reference library or a family video collection.

**User story:** As Diego, I want my team to share one tagged reference library, so that anyone can find and reuse clips another editor already downloaded.

**Scenario:** Diego shares his "Drone footage" collection with the team. An editor searches it, finds a harbour shot Diego downloaded months ago, and uses it without downloading it again.

**Acceptance criteria:**

- Collections can be shared with chosen members, read-only or editable.
- Shared collections include tags, transcripts, summaries and search.
- Files are accessed from the shared engine, not copied, unless a member saves a local copy.
- Activity is shown (who added or removed items), and changes can be undone by editors.

## Business and enterprise

These five features are what organisations need before they'll buy software for their staff: central control, security and easy rollout.

### F-117 Team and workspace management

**Business and enterprise · v4.0 · Team**

**What it is:** An admin console where an organisation manages its workspace: adding and removing staff, grouping them into teams, assigning licences and engines, and seeing usage across the company.

**User story:** As Lerato, I want one place to manage everyone's access and licences, so that onboarding and offboarding staff takes minutes, not a day of chasing.

**Scenario:** A new video team of 12 joins Lerato's company. She creates a "Video" team, invites all 12 by email, assigns them licences and the shared studio engine, and they're working the same afternoon.

**Acceptance criteria:**

- A web-based admin console for workspace owners and admins.
- Invite users by email or in bulk by CSV; group them into teams.
- Assign and reclaim licences; see seats used and available.
- Usage overview by team and user (data, downloads, active devices).
- Removing a user revokes their access on every device within 5 minutes.

### F-118 Central policies (allowed sites, bandwidth caps)

**Business and enterprise · v4.0 · Team**

**What it is:** Admins set rules that apply to everyone or to particular teams and can't be changed by individual users: which sites are allowed or blocked, bandwidth limits, where files may be saved, and which features are available.

**User story:** As Lerato, I want to block risky download sources and cap bandwidth during office hours, so that the app follows company security policy and doesn't slow the network.

**Scenario:** Lerato blocks downloads of executable files from outside an approved list of sites, caps each user at 10 MB/s from 08:00 to 17:00, and disables cloud AI features for compliance. The settings appear locked in every staff member's app.

**Acceptance criteria:**

- Policies for: allowed and blocked sites, allowed file types, bandwidth caps and schedules, save locations, and enabled features.
- Policies apply per workspace or per team, and override personal settings.
- Locked settings are shown in users' apps with a note that the organisation manages them.
- Policy changes reach all devices within 5 minutes.
- Blocked downloads give users a clear message explaining the policy.

### F-119 Audit logs

**Business and enterprise · v4.0 · Team**

**What it is:** A tamper-resistant record of important actions in the workspace (who downloaded what and when, admin changes, policy changes and sign-ins), for security reviews and compliance.

**User story:** As Lerato, I want a log of downloads and admin changes, so that I can investigate a security incident or answer an auditor's questions.

**Scenario:** A malware alert fires on one staff laptop. Lerato searches the audit log and finds the infected installer was downloaded from a blocked site before the block was added, by which user, and at what time.

**Acceptance criteria:**

- Logs downloads (source, file, user, time), admin and policy changes, and sign-ins.
- Searchable and filterable by user, team, action and date.
- Exportable as CSV and JSON, and can be streamed to the company's security tools.
- Entries can't be edited or deleted by admins; retention period is configurable.
- Logging scope is shown to users, in line with privacy laws.

### F-120 SSO login

**Business and enterprise · v4.0 · Team**

**What it is:** Staff sign in with their company account (single sign-on) through the organisation's identity provider, such as Microsoft Entra ID, Google Workspace or Okta, instead of separate passwords.

**User story:** As Lerato, I want staff to sign in with their company accounts, so that access follows our existing security rules and ends automatically when someone leaves.

**Scenario:** Lerato connects the workspace to Microsoft Entra ID. Staff now sign in with their company login. When an employee leaves and their company account is disabled, their access to the app ends automatically.

**Acceptance criteria:**

- Supports SAML 2.0 and OpenID Connect, tested with Microsoft Entra ID, Google Workspace and Okta.
- Users are created and removed automatically from the identity provider (SCIM).
- Admins can require SSO for everyone in the workspace.
- Company multi-factor authentication rules are respected.

### F-121 IT deployment tools (MSI, MDM)

**Business and enterprise · v4.0 · Team**

**What it is:** Installers and settings packages built for IT departments, so the app can be installed and configured on hundreds of computers at once using the tools companies already use (such as Microsoft Intune, Jamf or Group Policy).

**User story:** As Lerato, I want to install and configure the app on 200 computers silently, so that staff get it set up correctly without anyone visiting each desk.

**Scenario:** Lerato uploads the MSI package to Intune with a settings file that pre-connects each install to the company workspace. Overnight, it installs silently on every Windows laptop, and staff find it ready the next morning.

**Acceptance criteria:**

- MSI installer for Windows and a PKG for macOS, both supporting silent installation.
- Settings can be pre-configured (workspace, policies, browser extension) through MDM profiles or Group Policy templates.
- Browser extensions can be force-installed through company browser policies.
- Updates can be controlled by IT (automatic, delayed or manual).
- Deployment guides for Intune, Jamf and Group Policy.

## Business model

These two features add business revenue and give plugin developers a reason to build on the platform.

### F-122 Team and enterprise plans

**Monetization · v4.0 · Business model**

**What it is:** Paid plans for groups: a Family or Team plan for small groups sharing an engine, and an Enterprise plan with the admin, policy, audit, SSO and deployment features (features F-117–F-121), priced per user with invoicing.

**User story:** As Lerato, I want a business plan with central billing and admin features, so that I can buy licences for the whole company through our normal purchasing process.

**Scenario:** Lerato's company requests a quote for 200 seats. They sign up for the Enterprise plan with annual invoicing, a purchase order, and a support contact, and she assigns seats from the admin console.

**Acceptance criteria:**

- Family plan (up to 6 people), Team plan (per user, monthly or yearly), and Enterprise plan (per user, annual, with invoicing).
- Volume discounts and a self-serve trial for Team plans; a sales contact for Enterprise.
- Central billing with invoices, purchase orders, and tax handled by the merchant of record.
- Seats can be added or removed at any time, with prorated billing.
- Enterprise includes priority support with response-time commitments.

### F-123 Paid plugins in the marketplace

**Monetization · v4.0 · Business model**

**What it is:** Developers can sell plugins in the marketplace (feature F-110), as a one-time purchase or subscription. We handle payments and tax and keep a share; developers get the rest.

**User story:** As a plugin developer, I want to sell my plugin to the app's users, so that I'm paid for maintaining it and can keep improving it.

**Scenario:** A developer publishes a plugin that integrates with professional editing software, priced at $9. Diego buys it in two clicks with his existing account, and the developer receives their share monthly.

**Acceptance criteria:**

- Plugins can be free, one-time paid, or subscription.
- Purchases use the user's existing account and payment method.
- The revenue share is published clearly.
- Developers get a dashboard of sales, installs, ratings and payouts.
- Refunds within 14 days are handled by us, without developers needing to step in.
